# Test Plan — Yummy Na Kha Menu Scan & Personalization

## 1. Scope

### In scope

The **one core workflow** is tested end-to-end for diners who cannot easily read Thai restaurant menus:

> Create an account and accept the required documents → save a food profile, with separate opt-in for sensitive restrictions → upload a Thai restaurant menu → extract dish names and prices using the team's OCR service → obtain English names and ingredients from the Thai dish guide → review Top Pick / Check First / Avoid results → select dishes → show the order in Thai.

**Returning-user entry:** sign in with the saved profile and upload a new menu. Editing preferences can also recategorize the current menu within the active session; this is not a saved-scan library. Restaurant staff read the Thai order screen and clarify ingredients; they do not need an account or restaurant-side setup.

All Must requirements **F1–F18 and F26–F28**, features **FE1–FE9**, and project rules **LR1–LR12** are in scope. Multiple images in one session (**F19**, Should) are included because the implementation supports that path. Exclusions are permanent scan history, recipe or pantry management, recommendation ratings, live camera scanning, voice output, other language pairs, and menus outside Thai cuisine. The app cannot verify restaurant preparation or cross-contact.

**Source of truth:** the [requirement spec, revised 27 October 2026](../01-requirements/01-spec/20260907-01-menu-scan-personalization.md), [feature acceptance criteria](../02-design/01-feature-list.md), [backlog](../01-requirements/backlog.md), [user journey](../02-design/02-user-journey.md), and [project rules](../../rule.md). The [Charter](../../YummyNaKha!%20-%20Charter.md) and [Brief](../../YummyNaKha_Project_Brief.md) establish purpose and users; their older external-AI descriptions are superseded by the dated spec. This plan follows the five-section structure, table columns, **TC1–TC15**, and **T1–T5** of the [What2Cook reference](https://docs.google.com/document/d/1PlhRY-IkgDf2qtV9CRzfpTfy8aL17sz4dj5XrKW7zY0/edit).

**Implementation reviewed:** repository revision `8ac4de8`, 27 October 2026. The [app README](../../YummyNaKha_App/README.md), API services, components, and Prisma schema show a Next.js/React web client, Next.js API, PostgreSQL/Prisma, and a self-hosted FastAPI/PaddleOCR service. OCR sends text boxes to the parser; the curated guide supplies dish data. The browser currently applies the matching rules and stores the active menu and selection in session storage. This differs from the [architecture description](../02-design/04-diagrams/03-architecture.md), which places matching on the server. Network isolation and reproducibility must therefore be verified, not assumed.

**Known gaps to test:** email/password sign-in exists, but OAuth is pending a provider decision (TC1). The Avoid reason selector is not a separate recorded sensitive-data consent gate (TC3); no current consent document is withdrawable (TC6). Word-based English names and ingredients for unlisted dishes conflict with the spec's Thai-only fallback (TC7/TC15). The failure screen lacks photo review/cropping (TC10). Processing clears image bytes after OCR; session-end cleanup, account deletion, and a separate traffic-log retention mechanism were not found (TC14). Stored analyses need checking against the categories actually rendered in the browser (TC13). These are findings from source review, **not executed test results**. Keep the required behavior as the acceptance criterion and record failures or blockers explicitly.

**Schedule:** the Charter places testing/Beta Review in **W9–W11** and final improvements/delivery in **W12–W14**. Complete guide review, fixture annotation and technical checks before the pilot; resolve critical findings between rounds; finish the additional NFR1 sessions before final reporting. Calendar dates and the OCR host are **TBD**. The reference's 28 October/4 November dates are not confirmed Yummy Na Kha appointments.

**Environment and tools:** use an isolated test database and disposable accounts, the project's installed dependency versions, the real local OCR service for accuracy/timing, and a controlled HTTP OCR stub for fault injection. Start with the README's `npm run db:deploy`, `npm run ocr`, and `npm run dev` against test configuration. Record build, guide/OCR versions, OS, browser, device, network, image size and server hardware. Exercise mobile Safari, mobile Chrome and desktop Chrome on recorded versions. The repository has `lint`, `build`, `guide:check` and `guide:coverage` scripts, but no automated test suite or test runner was found. Unit/integration harnesses and browser automation are **planned work**, not existing coverage; the guide checker is a diagnostic, not evidence that acceptance criteria pass.

**Entry and exit:** fixtures and expected outputs must be reviewed before execution. No real-user round starts before the Thai-literate guide review, the applicable technical cases pass, and no open catastrophic or critical safety/privacy defect remains. Use the reference's severity direction: **4 catastrophic, 3 major, 2 minor, 1 cosmetic**. NFR2–NFR5 thresholds must be met on the defined sets; NFR7 is monitored throughout scheduled sessions. Undefined targets remain TBD and cannot be marked passed. A missing implementation is a defect; an unavailable prerequisite is Blocked. Record Not run / Pass / Fail / Blocked, build, actual result, evidence and defect reference for each TC. A case passes only when every required assertion passes; do not count parameterized inputs as additional test cases.

### 3.2 UAT — task-based sessions with real users

Use the same **five tasks, T1–T5, in the same order**, from setup to reviewing a changed decision. Read only the scenario, not UI instructions. Supply a fictional preference card and a reviewed menu containing both suitable choices and warnings; do not ask participants to disclose medical information. Each participant uses a fresh test account. If an earlier task fails, record it before restoring a known starting state for the next task; record that reset separately.

**Session structure** (approximately 35–40 minutes): introduction and research consent (3 min) → current-method baseline for the T2–T4 decision (5–8 min) → T1–T5 with think-aloud (15–20 min) → SUS, and any confirmed additional instrument (3–4 min) → three-question interview (5 min). Run one pilot first; it does not count toward participant/session totals. Ask: “What was hardest?”, “What did the warnings mean to you?”, and “What would you change before using this in a restaurant?” Record quotations only when actually spoken.

**Baseline (“before”) capture:** give a comparable Thai menu and the same fictional preferences. Let the participant use their usual method (translation tool, pictures, or asking a staff-role facilitator). Time from revealing the menu to declaring two choices and any unresolved ingredient questions; count meaningful taps, searches, lookups and requests for help. Use a fixed response sheet for staff questions in both conditions. For the app comparison, time continuously from starting T2 to the two-choice decision within T4, including upload/processing and inspection in T3; record the subsequent Thai-screen preparation separately. Account setup and T5 are outside that paired decision metric.

Use two reviewed menus matched for dish count, price visibility and difficulty; alternate which menu is used for baseline/app across participants. Keep the app tasks in order. Log tools, device, build and menu assignment. This follows the reference's before-then-after approach, so practice/order effects remain a limitation; different menus reduce recall but do not remove it. Baseline and app are two conditions of the same task, not extra UAT tasks.

## 4. Metrics (required + optional)

### Required — task performance (P4 Impact evidence)

For each task T1–T5 and participant, record **independent success**, **time on task**, **errors**, assistance and completion/abandonment. Enter one spreadsheet row per participant (`U01`…) with task-specific columns, round/build, before/app decision time and step counts, and evidence links. Here “P4 Impact evidence” retains the reference's assessment label; it is not the requirement spec's pain ID P4.

Start each task timer after the scenario is read; stop at the success criterion, declared abandonment or a **five-minute observation cap**. The cap is a session rule, not a product-performance target. Stop earlier for a critical safety/privacy problem. Log network waits; do not subtract them from elapsed time. Assistance after failure may help the session continue but cannot turn the original attempt into an independent success. Preserve blocked/not-attempted values as missing with reasons, never zero seconds or a pass.

- **Task success:** independent successes / attempted tasks × 100, with counts and denominator for each task and round. Report blocked tasks separately.
- **Completion time:** median and range for successful tasks; report failed/abandoned elapsed times separately so quick failures do not appear efficient.
- **Before/after impact (NFR1):** paired decision times and steps for **15+ distinct real users**. Report medians, per-user differences and number faster with the app. For a valid completed pair, percentage reduction = (before − app) / before × 100. Report unsuccessful pairs and reasons separately. Baseline and improvement target remain TBD until measured; do not invent a reduction target.
- **Errors:** count wrong selections, misread prices, missed concerns, consent misunderstandings, navigation mistakes and system failures. Record task, observed behavior, severity 1–4, cause if supported, proposed fix and retest evidence. A safety misunderstanding is not hidden inside an average error count.
- **Engineering evidence:** retain raw numerators/denominators for TC9/TC15, all TC8 timings and TC10 scheduled uptime. Track each TC's execution status and requirements affected by failures/blockers; no pass percentage may omit blocked cases without showing their count.

Report rounds/builds separately. Compare Round 1 issues with Round 2 retests as **issue → change → observed outcome**. Different cohorts and a small convenience sample support descriptive findings, not proof of population-wide improvement. No results or participant responses are entered in this plan.

### System Usability Scale (SUS)

Use **SUS** to assess perceived usability after the five tasks. It complements observed performance; it does not establish extraction accuracy, allergy safety or faster decisions. **When given:** immediately after T5, before the interview, with no moderator coaching.

**The 10 items** use a five-point response scale: 1 strongly disagree, 2 disagree, 3 neutral, 4 agree, 5 strongly agree. Explain that “this system” means Yummy Na Kha, then present the reference's wording unchanged:

1. I think that I would like to use this system frequently.
2. I found the system unnecessarily complex.
3. I thought the system was easy to use.
4. I think that I would need the support of a technical person to be able to use this system.
5. I found the various functions in this system were well integrated.
6. I thought there was too much inconsistency in this system.
7. I would imagine that most people would learn to use this system very quickly.
8. I found the system very cumbersome to use.
9. I felt very confident using the system.
10. I needed to learn a lot of things before I could get going with this system.

Do not drop items or improvise translations. Use a documented, validated language version if needed and record which version was administered. Missing answers are flagged; do not fabricate or silently impute responses.

**Scoring (per user):**

- Odd items (1, 3, 5, 7, 9): response − 1.
- Even items (2, 4, 6, 8, 10): 5 − response.
- Add the ten contributions and multiply by 2.5 for a **0–100 score**, not a percentage. Score only complete questionnaires.

**Reporting (across users):**

- Report sample size, mean and sample SD overall and separately by round/build; disclose missing questionnaires. Seek at least ten complete questionnaires without coercing completion.
- Use the reference's **68 benchmark** for context; its Sauro/Lewis interpretation places 68 around average, ≥80.8 in grade A and <51.7 in grade F. This comparison is not an approved NFR8 pass threshold; that target remains TBD pending the first usability study.
- Plot per-user scores with the 68 benchmark and observed mean; identify rounds/builds. Make charts only after genuine scores exist.

**Analysis note:** link low usability ratings to observations such as difficulty distinguishing Check First from Avoid or finding Order in Thai, then document the change and retest. Report differences in SUS alongside the underlying task evidence.

**TAM / UTAUT2:** the supplied reference uses SUS. No independent assessment rubric requiring TAM or UTAUT2 was found in the Charter, Brief, spec, backlog or design documents. SUS and task performance are therefore the planned instruments. Before the pilot, QA and the Product Owner must check the course rubric; if an acceptance model is mandatory, select the required validated instrument and record its wording, scale, scoring and administration in a revision. Do not treat SUS as TAM, claim an unverified assessment requirement, or manufacture acceptance scores.

## 5. Real users

- **Who:** recruit diners who encounter Thai restaurant menus they cannot easily read, including international students/foreign residents where available. Recruit people with relevant food-restriction experience only voluntarily; use fictional profiles in all tasks. The earlier six-person survey did not establish respondents' nationality or medical status. Team members are facilitators, not substitute users; a classmate counts only if independently screened as a target user.
- **How many:** follow the reference's **5 users → fix → 5 more users**, achieving at least **10 moderated sessions**, then run **5 additional sessions** with the same five tasks and paired measurement to meet the Charter/NFR1 requirement of **15+ distinct real users**. Pilot participants are excluded. Prefer new users for each round; replacements must be reported rather than concealed. If anyone returns for a retest, that session does not increase the distinct-user count. Record the build used for every session and stratify results accordingly.
- **Consent:** explain purpose, voluntary participation, withdrawal, data use and retention before the session; obtain separate permission for recording. Keep research consent separate from in-app agreements. Use coded identifiers U01–U15 in analysis, store any signed consent separately with restricted access, and confirm a research retention/deletion date before recruitment. Use synthetic accounts and health examples; this is a simulated ordering exercise with no food consumption.
- **Roles per session:** one **Moderator** reads scenarios and uses neutral think-aloud prompts without pointing or solving; one **Note-taker** times, counts actions/errors and records observed statements. A Thai-literate reviewer verifies menu annotations, guide content and order-screen readability; name/date must be recorded before user testing. QA / Tester Aike Paung Bra coordinates evidence and defect tracking; Product Owner Tay Zar Tun confirms scenario expectations and scope decisions; the Tech Lead prepares the isolated environment. Moderator/note-taker assignments may rotate.

The deliverable from each round is a factual task/metric record, complete SUS responses where supplied, and prioritized observed issues linked to fixes and retests. Final reporting must state which requirements passed, failed or remained blocked, the actual participant counts and build versions, and the limits of the evidence. This document specifies planned testing only; it contains no claimed test execution, SUS score or user outcome.
